## 1. Verdict — GO_WITH_FIXES

Ship the pilot after a short, well-scoped fix list. The scope-safety machinery this server exists to provide is real and verified live: the session-token HMAC gate is correct in production, the operator-unscoped and recruiter-scoped paths behave as designed, the scope_handle and confirmation-token artifact layer is signed and subject-bound with genuine tamper/cross-subject/expired negative controls, and every fail-closed branch I could reach denies rather than serves. The green suite is not lying about safety. What it hides is one genuine functional defect and one class of missing regression locks, and both gate a clean GO rather than the safety of the deployed code. The functional defect is high severity but narrow: analyze_stage_latency reads a stage-entry timestamp that the live /v3/applications endpoint does not carry, so it returns empty rankings and a zeroed headline on every real call. The missing locks are medium: the single highest-blast-radius gate in the system survives total defeat against all 662 tests, and the revocation reader's real fail-closed branch survives being flipped open. Neither is a present-tense exploit, but both are precisely the regressable-auth-bug-behind-a-green-suite pattern the last audit of this package caught five times. The fixes are hours, not weeks. Do them and go.

## 2. Scope of the audit

Covered: the authorization and scope boundary (cross-recruiter PII), the session token / revocation / secrets path, fail-closed error handling and resource safety, data-shape correctness against the vendored raw Harvest v3 contract, test honesty (re-run plus mutation of the load-bearing assertions), scope_handle and resolve_job_scope integrity, the at-scale mirror funnel (the newest, highest-churn code), and the transport / deploy / observability / governance apparatus. Findings were verified by reading the cited code directly, cross-checking against the vendored v3 OpenAPI snapshot, and running mutation experiments (disable the signature check, flip the revocation branch to fail-open, neuter the flat job_id reader) to confirm whether the suite actually catches a regression.

Not covered, and called out explicitly in section 7: identity-directory lifecycle and deprovisioning correctness (the email-to-actor mapping itself, as distinct from the token that authenticates against it), audit content sufficiency for incident reconstruction, concurrency and load behavior in the stateless transport, Greenhouse rate-limit backpressure as a fleet property, intra-recipe permission-snapshot consistency under TTL=0, cross-instance clock skew, and supply-chain integrity of the gitignored reference client and the dev-toolchain-laden production image. These were reasoned about from the code but not exercised, and the most important of them — identity deprovisioning — is the headline of "the thing you're not seeing."

## 3. Production-readiness by area

**D1 — Authorization / scope boundary.** Built and correct in production. The gate ordering is right (signature verified before the payload is parsed or trusted), and cross-job scope is enforced by applicationIsPermitted on every read. Two residual items: the keystone signature gate carries no negative-control test (medium, treated under D2/D5), and filterCandidateRow has a fail-open asymmetry on its fetch branch (index.ts:709) where the embedded branch sanitizes but the fetch branch returns the row verbatim — latent only, because v3 candidate rows do not embed applications, so there is no live trigger.

**D2 — Auth, session token, revocation, secrets.** Built, with a cluster of unlocked branches. The live behavior is correct: signatures verify, revocation fails closed, the secret floor is enforced at issuance and readiness. The gaps are all coverage and posture: no signature negative control, no real non-2xx revocation fail-closed lock, immortal revoke-only tokens by deliberate design, and a length-only (no entropy) secret gate. None is a live vulnerability; together they are the area that most needs regression locks and an explicit model-acknowledgement before pilot.

**D3 — Fail-closed error handling & resource safety.** Mostly built, one real laundering bug. The secondary application-to-job lookup swallows a genuine PERMISSION_LOOKUP_FAILED denial into the same "unresolved" exclusion bucket as a benign missing-job gap and returns ok:true with zeroed metrics (medium) — an upstream auth failure mislabeled as routine data quality, and the regression test for it is absent because the existing tests deny all reads so the primary denies first. The remaining D3 items (timeout does not cancel the underlying Harvest read; rate limiter bounds only tool-call budget, not pre-tool work; rate limiter is in-memory per-process; mirror pager has no deadline) are all low and self-limiting, and the caller always fails closed with a clean TOOL_TIMEOUT and no stale data.

**D4 — Data-shape correctness on raw Harvest v3.** This is the area with the one true functional defect and one mislabel. The high: analyze_stage_latency computes dwell from a current-stage-entry timestamp that the vendored /v3/applications schema (additionalProperties:false, only created_at/updated_at/rejected_at/last_activity_at) never returns; stage timing lives exclusively on /v3/application_stages, which the tool never queries, so observations are empty in production and the headline reports aging_applications:0 with no inline caveat. The low: fixtures-production-shapes.ts has its prose backwards — it calls the NESTED shape "production" when the vendored contract proves FLAT is production — but the readers are flat-first and the flat contract is in fact locked by real output assertions (I confirmed by neutering the flat job_id branch and watching pipeline-quality.test.ts go red), so this is a comment-accuracy bug, not a GO-gate risk.

**D5 — Test honesty.** The mutation experiments are the verdict here. Replacing signatureMatches with `return true` leaves all 662 tests green; flipping the revocation non-2xx branch to `return false` leaves the relevant 88 green; neutering the flat reader correctly goes red. So the suite genuinely locks the data-shape contract but genuinely does not lock the two most security-critical branches. The honest read: the green suite is trustworthy about shapes and untrustworthy about the auth gate.

**D6 — scope_handle / resolve_job_scope integrity.** Built and well-defended on its own layer — the artifact signer has tamper, cross-subject, and expiry negative controls, redemption re-intersects live permissions and fails closed on truncation, and revoked jobs drop out. Two caveats: every handle property is subject-bound to runtime.session.subject, which is minted from the unlocked session signature (so the capability model inherits that one gap), and a missing scope-signing secret falls back to a per-process ephemeral key instead of failing closed — harmless today because /readyz enforces the secret, but it would silently dead-end 100% of redemptions under the per-request stateless transport if the secret were ever unset. jti is present on payloads but never enforced (info — decorative, no replay escalation since redemption re-validates).

**D7 — At-scale mirror funnel.** Dormant by config (MIRROR_NOT_CONFIGURED), so nothing here is live. The code is conservative-by-design: the channel-less default cries wolf (stamps fresh data "NOT current" when a sibling channel never synced) but fails safe and has a working single-channel escape hatch; the facts read truncates at 5000 with no ORDER BY so a broad scope returns an arbitrary non-reproducible slice, but truncation is disclosed loudly and confidence is forced to low; partial mid-funnel entry shows as 100% conversion but the growth is visible in the adjacent reached field. All low or info, all gated behind dormancy, all to be revisited before the mirror flips live (including threading the ToolDeadline into the unbounded pager).

**D8 — Transport, deploy, observability, governance.** Built but governance is advisory rather than enforced. The 2275-line rollout gate is run only when a human remembers (medium); audit durability is unprovisioned on the actual Render target (medium); the deploy packet describes AWS infra the service does not run on and the drift-check command does not contact the deployed catalog (low); several gate metrics are decorative (leakage auditEventCount reports check count, not events; scope_signing_secret missing from the required-checks list; readyz public-dev branch leaks config posture). The pattern is the same one this repo has hit before — elaborate apparatus that is not CI/deploy-enforced.

## 4. Cross-cutting concerns

**Scope / authz.** The boundary is correct where it executes. The risk is not a present hole but a missing lock on the gate and an unaudited mapping behind it — the directory the gate authenticates against has no deprovisioning path, which is the section-7 headline.

**Auth / secrets.** Correct live behavior, three unlocked or unbounded properties (signature, revocation non-2xx, token age) and two posture choices (length-only secret, revoke-only tokens) that want explicit sign-off. The mutation tests make the coverage gap undeniable.

**Fail-closed.** Strong as a default — timeouts, missing secrets at readiness, revocation-unverifiable all deny. The one place it launders rather than fails is the D3 secondary-lookup denial, and that one is worth fixing because it converts an auth outage into a confident clean bill of health.

**Data-shape.** The original NO-GO class is genuinely closed for the readers (flat-first, nested-tolerant, locked by assertions), with one shipped consequence the shape-fix missed: a tool whose entire input field does not exist on the real endpoint. That is a contract-coverage gap, not a reader bug.

**Test-honesty.** The suite locks shapes, not the auth gate. Two one-hour negative-control additions close the dangerous half.

**Transport / deploy.** Runtime is correct; the governance and durability wrapping around it is documentation-grade, not enforcement-grade. Audit durability is the one with real consequence for a PII system.

## 6. Adjudication of the four known-open items

**(a) Get-by-id UNPERMITTED negative control — effectively CLOSED at the engine, with a residual asymmetry, not the gap as framed.** The scope engine denies unpermitted records via applicationIsPermitted / filterApplicationBackedRow on every get and search path; cross-job access is enforced, not served. The one live-adjacent concern is filterCandidateRow's fetch branch returning the row verbatim (index.ts:709) where the embedded branch sanitizes — but that is gated behind a non-v3 precondition (candidate rows do not embed applications in v3), so it is latent defense-in-depth, not an open unpermitted-serve. Treat (a) as closed for pilot, fix the asymmetry in the hardening pass.

**(b) Leaf-provider real-error fail-closed controls + session-signature negative — OPEN.** This is the live one. The session-token signature negative control does not exist anywhere (confirmed by grep and by the `return true` mutation passing 662/662). The Supabase revocation reader's real non-2xx branch is exercised by nothing (the timeout test aborts before response.ok is read; the only other case is a fake that throws). These are blockers #2 and #3. The HMAC-verify and JSONL-audit-sink fail-closed paths are partially covered but the signature and revocation negatives are the load-bearing ones and they are open.

**(c) Shared-secret end-to-end resolve→analyze — CLOSED.** The v2 thesis is proven by test. analysis-scope-integration.test.ts mints a scope_handle on the resolver side and redeems it on the analysis side, with tamper/cross-subject negatives (analysis-scope-integration.test.ts:136-143), so a handle is genuinely minted under one signer and accepted under the same signer across the boundary. The artifact path is the well-locked layer. The only caveat is structural, not test-coverage: at runtime under the stateless transport a missing scope-signing secret would split the signer per request — but /readyz enforces the secret, so the handoff works live and the exchange is proven.

**(d) Live Harvest v3 contract probe gating distribution — OPEN, and now demonstrably necessary.** The rollout gate validates self-reported evidence JSON and never re-executes a probe or contacts the live MCP (rollout-gate.ts has no fetch/http/spawn anywhere). More pointedly, the stage-latency probe (probe.ts:503-527) returns status:pass whenever the call is ok and never asserts applicationsConsidered > 0, so the D4 high — an all-zero empty success — ships green straight through REQUIRED_LIVE_PROBE_CHECKS. A live contract probe that asserts non-empty results on a known-populated job would have caught the stage_latency bug. This item is open and its absence is exactly why blocker #1 reached "live on Render."

## 7. The thing you're not seeing

The audit proved the identity gate is correct. It never asked whether the thing the gate authenticates to is trustworthy or kept current — and that is where the real cross-recruiter exposure lives.

The session token carries an operator-asserted email and subject; "verified" means issued against a roster, with no holder challenge (email-session.ts:128,215). The binding from that email to a Greenhouse user id comes from recruiter_identity_directory, populated by applyIdentityBootstrapPlan (identity-bootstrap.ts:167-200) as an INSERT/UPDATE-only merge-duplicates upsert keyed on greenhouse_user_id. It never tombstones and never deletes. Deactivation is checked once, at the moment a plan is generated (identity-bootstrap.ts:127-130); a recruiter deactivated in Greenhouse after that run keeps a status:resolved row forever, and createSupabaseIdentityDirectory (identity.ts:156-185) keeps resolving it. So normal HR offboarding — deactivate in Greenhouse — does nothing to this system. Combined with the immortal-token finding, an offboarded recruiter retains full scoped PII reads until a human manually recovers and revokes that exact tokenId. And a recycled or reassigned work email, a manual directory edit, or a merge-duplicates collision on greenhouse_user_id silently maps one human onto another's permitted-job pipeline, invisible to every auth check: signature valid, token not revoked, status resolved. Grep finds no job and no test that reconciles the directory against current Greenhouse active/inactive state or current email. The whole scope model rests on this table being correct and current, and nothing keeps it so.

Three more uncovered classes compound it, each named here so they are not lost. Audit content is insufficient for incident response: RecruiterAuditEvent records only counts (audit.ts:15-38), never the candidate/application/job ids returned, and the MCP, Greenhouse-client, and token-error correlation ids are three disjoint schemes that never chain — so the trail can say "47 rows at time T" but not which 47 data subjects, which makes a breach-scope determination impossible from the audit alone, even though the gate treats that audit as evidence. Concurrency is entirely untested: the process-global OAuth app token has no in-flight dedup (../src/auth.ts:45-87, a refresh herd at cold start), the 429 retry is un-jittered and shares one fleet-wide budget (synchronized retry storms), and concurrent appendFile writes to the audit JSONL (audit.ts:95-99) are untested for line-tearing — every suite is single-call. And the scope engine rides ../../dist/client.js, a gitignored build artifact rather than committed source, shipped in an image built with npm ci --include=dev --no-audit, with no SBOM, no lockfile vulnerability gate, and no dependency review — a green app over an unverified substrate.

For a one-instance, two-recruiter pilot none of these detonate. But the identity-deprovisioning gap is the one I would not carry into a wider pilot: it is the spoofing-across-the-mapping and offboarding class the scope model actually depends on, and it is invisible to all eight dimensions the audit ran.

## 8. Prioritized next moves and the call

Highest leverage first, by blast radius per hour of work. Blocker #1 (stage_latency) is the only thing a pilot recruiter will actually experience wrong, so fix or gate it before anyone runs it — gating closed is a one-hour stopgap if re-sourcing from application_stages slips. Blockers #2 and #3 are two hours total and they convert the two mutation-survivable auth branches from "correct but unguarded" to "locked," which is the single cheapest reduction in regression risk on the whole surface; do them in the same sitting. Blocker #4 (two to three hours) stops an upstream auth outage from reading as a clean bill of health. Blocker #5 (two hours) is the difference between a scope-safe-but-unauditable pilot and an auditable one — non-negotiable for a PII system, cheap to satisfy with a Render disk. Blocker #6 wires the governance gate so it can actually block a deploy. Blocker #7 is mostly a sign-off plus an optional max-age gate. The full list is roughly one to two engineer-days.

Beyond the blockers, the highest-leverage non-gate move is a directory reconciliation job and a deprovisioning path (section 7) before the pilot widens, plus a live contract probe (known-open item d) that asserts non-empty results — that single probe would have caught blocker #1 and is the right permanent guard against the v3-shape class recurring.

The call: GO_WITH_FIXES. The deployed code is scope-safe and the green suite is honest about that; it is not honest about the auth-gate regression locks, and it shipped one tool whose input does not exist on the live contract. Close the seven items above — most of them hours — and this is a clean pilot GO.
