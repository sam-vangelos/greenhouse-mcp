# Harvest v3 Contract Realities and Live-First Read Architecture

The read plane in `packages/scoped-core` and `packages/recruiter-mcp` is shaped around a few specific properties of the Greenhouse Harvest v3 API. Understanding why the server is structured the way it is starts with what Harvest v3 actually does on the wire, where its contract differs from Harvest v1/v2 assumptions, and why the server queries Greenhouse live rather than maintaining a general local mirror of candidate data.

## Why Per-Recruiter Scoping Must Live in the MCP Server

Harvest v3 authenticates custom integrations through OAuth 2.0 client credentials (`POST https://auth.greenhouse.io/token`), where the token's `sub` claim identifies a Greenhouse user ID. On list endpoints, however, Harvest v3 requires the authorizing user to be a Site Admin and performs no per-recruiter row-level filtering on reads. A non-admin `sub` cannot list resources directly, and a Site Admin `sub` sees the entire organization.

That single API rule forces the architecture in `packages/scoped-core/src/index.ts`. The raw Harvest client (`packages/control-plane/src/client-readonly.ts`) reads with a read-only credential, and `scoped-core` enforces the caller's actual Greenhouse access before any row reaches a tool projection:

1. `createHarvestPermissionProvider` (`packages/scoped-core/src/index.ts`) queries `/v3/user_job_permissions` (`user_ids`) and `/v3/user_roles` (joining `role_id` to `role_type === "site_admin"`), while `createSiteAdminAwarePermissionProvider` (`packages/recruiter-mcp/src/site-admin-permission.ts`) checks `/v3/users` (`site_admin: true`, `deactivated` not true) and computes confidential-job exclusions when a Site Admin is not assigned to a confidential requisition. Permissions are resolved on each read by default (`GREENHOUSE_RECRUITER_FORCE_PERMISSION_TTL_ZERO=true`, `GREENHOUSE_RECRUITER_PERMISSION_TTL_MS=0`), with optional single-flight TTL memoization in `packages/recruiter-mcp/src/ttl-memo.ts` (`createTtlMemo`). If the permission read fails, `scopedRead` fails closed with `PERMISSION_LOOKUP_FAILED`.
2. Every read tool in `DEFAULT_FILTER_REGISTRY` (`packages/scoped-core/src/index.ts`) is classified by how its records tie back to a job: directly job-scoped rows (`/v3/jobs`, `/v3/job_interview_stages`, `/v3/job_owners`, `/v3/openings`), application-backed rows (`/v3/applications`, `/v3/interviews`, `/v3/scorecards`, `/v3/offers`, `/v3/application_stages`), candidate-backed rows (`/v3/candidates`, `/v3/notes`, `/v3/attachments`), or global reference dictionaries (`/v3/sources`, `/v3/rejection_reasons`, `/v3/departments`, `/v3/offices`, `/v3/users`).
3. Candidate privacy (`candidate.is_private`) and private custom fields (`custom_fields` entries marked private in `/v3/custom_fields`) are evaluated separately from job membership (`scoped-core` and `packages/recruiter-mcp/src/private-custom-fields.ts`). When an operator attestation is required and absent, private candidates are withheld (`packages/recruiter-mcp/src/private-candidate-attestation.ts`, `packages/recruiter-mcp/supabase/migrations/0008_private_candidate_attestation.sql`).

## Harvest v3 Wire Rules and Schema Shifts

Several places where Harvest v3 differs from older Greenhouse integrations are encoded directly into the client, the generated endpoint registry (`packages/recruiter-mcp/src/harvest-v3-registry.generated.ts`, covering 72 GET endpoints), and the contract test harness (`packages/recruiter-mcp/test/support/harvest-contract.ts`):

- Cursor pagination follows the `Link: <...>; rel="next"` response header (`per_page` up to 500). Unlike initial list requests, a cursor follow-up request must pass `cursor` as its sole query parameter; resending filter parameters alongside `cursor` causes Harvest v3 to reject the request with HTTP 422. `packages/recruiter-mcp/src/read-all.ts` and `packages/control-plane/src/client-readonly.ts` enforce cursor-only follow-ups.
- Parent-ID filter parameters such as `job_ids`, `application_ids`, and `candidate_ids` cap comma-separated lists at 50 IDs per request. When a confirmed scope spans more than 50 requisitions, `packages/recruiter-mcp/src/tools/application-job-lookup.ts` chunks fan-out reads in batches of 50 rather than letting Harvest reject the query.
- Rate-limit backoff in `packages/control-plane/src/client-readonly.ts` honours `X-RateLimit-Remaining`, `X-RateLimit-Reset`, and `Retry-After` on HTTP 429 (`MAX_RETRIES = 3`, `DEFAULT_RETRY_SECONDS = 30`, `MAX_RETRY_SECONDS = 120`, and per-request timeout `GREENHOUSE_REQUEST_TIMEOUT_MS` defaulting to 20,000 ms).
- Application rows in `/v3/applications` no longer embed a `current_stage` object, and the `stage_id` field on an application row is a per-application stage-instance ID rather than a shared job-interview-stage ID. Filtering `/v3/applications` by `stage_ids=<job_interview_stage_id>` returns zero rows without an error; selecting a stage bucket requires the `job_interview_stage_ids` query parameter (`packages/recruiter-mcp/test/support/harvest-contract.ts`).
- Candidate activity is split across resources: prose notes and emails live on `/v3/notes` (with a `type` discriminator and visibility flags), while stage transitions live on `/v3/application_stages`. Scorecard verdicts use `candidate_rating` rather than v1's `overall_recommendation`, and `/v3/scorecards` links to candidates through `application_id` rather than a direct `candidate_id`.

## Why Reads Are Live-First Rather Than Mirrored

Harvest v3 offers no server-side joins or aggregations, so analytical questions ("which interviewers have overdue scorecards across my six backend requisitions?") require fetching the underlying rows and reducing them in server code. One design alternative is to back these tools with a synced Postgres mirror of Greenhouse applications, stages, and scorecards.

The recruiter MCP instead stays live-first against Harvest v3 without a general data mirror.

A local mirror of candidates, applications, notes, and scorecards creates a second datastore holding candidate personal data and requires replicating Greenhouse's permission and privacy rules in SQL. Querying Harvest v3 live through `scoped-core` means permission revocation in Greenhouse takes effect immediately (or as soon as an optional short in-memory permission memo expires), and candidate PII is never persisted in the MCP's Supabase project.

Scoped volumes also fit within interactive budgets. Because `resolve_job_scope` bounds analytical queries to a recruiter's confirmed requisitions, and because `read-all.ts` requests `per_page=500` with chunked 50-ID fan-out and deadline-aware backoff, recruiter-scoped analytical queries complete over live REST without needing a warehouse sync.

Finally, explicit completeness beats silent staleness. A mirror trades live pagination limits for sync lag and backfill gaps. On the live path, `packages/recruiter-mcp/src/read-all.ts` never treats an arbitrary page cap as a complete dataset: if a request hits its deadline or a rate-limit ceiling before exhausting `rel="next"`, the tool marks `completeness.status` as `"incomplete"` or `"partial"` in the response envelope so the caller sees exactly what was read and what was omitted.

## The Single Durable Exception: Weekly Stage-Stock Logbook

There is one analytical question that live Harvest v3 data cannot answer even with complete pagination: historical stage stock ("how many active applications were sitting in each stage of this requisition two weeks ago?").

On `/v3/application_stages`, `entered_at` and `exited_at` are populated once an application moves, but `entered_at` is frequently `null` on currently active stage rows. Because the live API does not expose when those applications entered their current stage, past stage headcounts cannot be reconstructed retroactively from `/v3/application_stages`.

To close that single gap without building a candidate mirror, `packages/recruiter-mcp/src/pipeline-snapshot.ts` and `packages/recruiter-mcp/supabase/migrations/0002_pipeline_state_snapshot.sql` through `0005_pipeline_snapshot_stage_name_grain.sql` implement an optional weekly logbook (`pipeline_state_snapshot`, gated behind `GREENHOUSE_RECRUITER_SNAPSHOT_ENABLED`). Each sweep records only aggregate active counts keyed by `(period_key, greenhouse_job_id, stage_name)` (using `bigint` for Greenhouse IDs and the shared `stage_name` rather than the per-application `stage_id`, with `''` as the job-level rollup sentinel). It stores zero candidate IDs, application IDs, or personal data, and when the table is disabled or has no prior week for a requisition, `analyze_pipeline_quality` reports the current snapshot while stating why week-over-week delta is unavailable.
